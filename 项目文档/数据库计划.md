### 1. 先修复和复用，不从零重建

核对现有迁移、实际表结构、数据量及权限，恢复研发数据库稳定持久化连接，保留已有业务数据和已完成的数据库功能。实际部署库名以经过核对的配置为准，不因本文中的示例名称擅自新建或替换数据库。

### 2. 同机部署、容器分离

网站和数据库放在同一台服务器，网站与 PostgreSQL 使用独立容器。初期运行一个 PostgreSQL 实例，在其中保留研发和工资两个逻辑数据库：

```text
同一台服务器
├── 网站服务：统一网站入口
└── PostgreSQL 容器：一个数据库实例
    ├── 研发数据库
    └── 工资数据库
```

一个实例是一个 PostgreSQL 服务，并不意味着把所有表混在一起。两个逻辑数据库保留各自的表、账号及访问权限，共享数据库服务和服务器资源。实例停机时两部分业务都会受影响；以后可按容量或隔离需要拆成独立容器。

数据库使用持久化卷，通过内部网络供网站后端连接，不向公网开放数据库端口。迁移账号与运行账号分离，网站使用最小权限运行账号。网站数据库连接配置、密码和企业微信凭据只保存在服务器端。

## 四、企业微信身份与访问权限

### 1. 身份核验

使用企业微信登录识别访问者。后端验证企业及成员身份，通过企业微信官方接口核对部门与经理资格，不根据浏览器提交的姓名、职位或部门直接授权。

“经理”默认采用企业微信专用“经理”标签成员作为授权依据，正式部署时绑定实际标签 ID；“财务部”绑定实际部门 ID，包含其下级部门成员。标签是本计划的默认实现方式，部署前需核对企业微信实际配置，不按职位文本模糊匹配权限。

### 2. 权限矩阵

| 访问者 | 研发业务 | 工资相关界面和数据 |
| --- | --- | --- |
| 本企业经理 | 可访问全部现有业务界面 | 可访问，包括个人工资与归集明细 |
| 本企业财务部非经理 | 可访问获准研发业务及项目人工费用汇总 | 不呈现工资菜单，禁止访问工资页面、接口和文件 |
| 未登录、其他企业成员、非财务部且非经理 | 默认不开放业务访问 | 禁止访问 |

首页向财务部非经理隐藏整个“工资表”菜单，包括自动算薪、人员归集、历史批次、邮件发送和核算规则。权限必须同时落实到页面、接口、下载与归档文件；直接输入地址或调用接口也不能绕过。

研发接口向财务部非经理仅返回获准的项目汇总，不返回个人工资明细、原始工资文件、个人工资快照或可反查工资的链接。图表、导出及错误提示同样执行该规则，不只隐藏前端字段。

### 3. 会话与权限更新

使用服务器端会话保存身份，每次受保护请求检查权限。企业微信资格最多缓存 5 分钟，过期后重新核验；核验失败时不开放受限功能。退出登录立即使对应会话失效。新增会话接口返回当前用户及可访问业务能力，首页据此呈现菜单，后端独立授权。

现有研发接口密钥不得替代用户身份与权限检查，前端不得保存能绕过权限的通用密钥。管理员、经办、复核等操作角色在企业微信访问资格之内细分，非经理不能因为操作角色而取得工资权限。

## 五、共通数据：研发人员工资与人工费用

### 1. 权威来源和统一人员标识

工资作为工资金额的权威来源。研发人工费用引用已确认工资批次并保存归集快照，不维护另一份可以独立修改的工资。

每个人使用稳定的内部人员 ID，并关联企业微信成员 ID。工资人员和研发人员通过内部人员 ID 对应，不只靠姓名匹配。首次接入核对已有人员标识，沿用可用主键，通过明确映射关联两库；未匹配或重复匹配人员进入待处理清单，不自动猜测归集。人员离职或姓名变化不切断历史关联。

### 2. 归集口径和分摊依据

仅已确认工资批次可以进入正式研发归集。后端读取研发人员相应月份的工资，以及人工费用规则允许计入的单位承担社保、公积金等项目，再按项目工时比例分摊。

人工费用不默认等于实发工资。具体纳入哪些工资项目、单位承担费用、期间及舍入方式，通过版本化规则确定。实施时先对照现有核算规则，未经口径核对不能直接套用新规则确认结果。

没有有效人员映射、费用口径或工时依据时，提示待处理并禁止确认该归集结果，不自动平均分摊。同一人员同月分摊比例合计不得超过 100%；不足 100% 的余额明确记录为未归集费用。金额使用定点精度，并记录分摊舍入差额。

### 3. 可追溯快照与重复保护

每条研发人工费用记录保存来源人员、月份、工资批次及版本、人工费用规则版本、分摊依据、项目和金额。归集快照用于追溯和复核，不允许在研发侧直接改写来源工资。

以来源工资版本、归集范围和目标项目等业务键建立幂等保护，同一次同步或失败重试不能重复入账。归集金额与来源可归集金额勾稽，项目归集、未归集余额和舍入差额应完整解释来源金额。

### 4. 跨库同步与修订

两个数据库之间由网站后端执行受控读取与同步，不让前端直接跨库取数，也不将普通单库事务误认为跨库原子事务。

同步任务记录来源批次版本、目标范围、执行状态、错误和重试次数。目标库写入采用事务和幂等键；失败可重试，工资确认不会因研发同步失败而被悄悄回滚。同步期间固定来源版本，确认前再次核对其有效状态；只有同步完成且金额核对通过，研发归集结果才可确认。

工资修订产生新版本，不静默覆盖已归集结果。未确认研发结果可明确触发重新计算；已确认研发结果保留原快照，标记来源版本变化，经授权修订生成新结果版本，保留前后关系与审计记录。

### 5. 数据共通不扩大权限

工资到研发的同步使用后端受限服务权限，普通财务成员不因此获得工资库访问权。经理可以追溯个人工资与归集明细；财务部非经理只能查看获准的项目人工费用汇总。涉及工资来源明细的人工操作和下载仍要求经理权限。

## 六、业务后端与文件持久化

- 研发：完善项目、平台、原始资料、导入、核算批次、月度结果、确认和导出归档。
- 工资：完善人员、规则版本、核算批次、来源文件、确认和历史追溯。
- 导入、计算结果写入和确认采用事务，增加数据校验、重复提交保护、并发冲突处理和明确失败提示。
- 保存关键操作审计，包括操作者、时间、业务对象、来源版本及操作结果，日志不记录密码或完整工资明细。
- 原始文件与导出文件保存在服务器持久化目录，数据库保存位置、校验值、业务关联和权限信息。受限文件通过鉴权接口下载，不直接放在公开静态目录。

## 八、测试与验收标准

- 数据库迁移目标正确、可重复执行且无重复应用；事务失败回滚，不产生半份业务数据。
- 刷新页面和重启网站、数据库服务后，业务记录及归档文件仍可读取。
- 从 3220 首页菜单逐项实际点击验收，不以只访问独立路由替代。
- 经理可打开全部现有业务界面；财务部非经理看不到工资菜单，直接访问工资页面、接口、导出和文件均被拒绝。
- 验证伪造身份、过期会话、经理资格撤销、其他企业成员及企业微信核验失败场景。
- 验证研发页面、接口及导出不向非经理泄露个人工资信息。
- 验证人员同名、姓名变更、离职及映射缺失场景，历史关联保持正确。
- 验证工资确认、同步失败重试、重复归集、工时不足或超额、跨项目分摊及金额舍入勾稽。
- 验证工资新版本出现后的提示、未确认结果重算和已确认结果修订，历史快照不被覆盖。
- 不启动额外网站服务，不修改其他项目目录，不提交敏感信息或无关变更。

## 九、备份与上线边界

数据库默认每日备份，保留最近 30 天；文件持久化目录同步纳入备份，制定与数据库记录相匹配的恢复流程，并执行恢复验证。正式上线前配置异机备份目的地，避免同一服务器故障导致数据和备份一起丢失。

GitHub 保存代码与部署方案，实际数据库内容通过单独备份恢复或受控导入迁入服务器。服务器地址当前不需要；迁移、发布和对外操作在相关配置明确后执行。本文不授权邮件发送等额外外部操作。
